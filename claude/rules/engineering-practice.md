How to work on code and config, learned from sessions that went wrong. About the work, not the user: user preferences live in `interaction-style.md`, repo conventions in `github-templates/project-standards.md`.

- **Verify before suggesting.** Check that an API, flag, or command exists before proposing it; an unverified suggestion that errors wastes a round-trip. The same goes for predictions about a repo, such as "this merge will conflict": check its docs and config first. On 2026-11-11 a session predicted a log conflict that the repo's `.gitattributes` union merge prevents, and the repo's documented merge procedure was never read. If every agent would have to make the same check, it is better to state the answer in the repo, where agents read first.
- **Prefer a tool's incremental mechanisms** (update, sync, migrate) over destructive resets.
- **Edit files with the Edit and Write tools, not `sed`, a heredoc or a one-off script.** The user reads the diff, and does not want arbitrary scripts rewriting files (2026-11-10; their father's objection too). The exception is a rename or other mechanical change across many files, where a script is how thoroughness is checked: say so first, then show what it touched.
- **Back up before scripted edits** to a file holding uncommitted work, and read the whole file before opening it for writing. An in-place rewrite that opened the file first emptied it, and recovery depended on a stale export.
- **Clean inherited or generated code at the level of effect, not names.** Ask whether each rule or branch actually applies, and prove the result equivalent mechanically (e.g. compare computed output before and after) instead of calling it cleaned up. A rename-and-prune pass on an exported stylesheet left ~40% dead rules behind.
- **Confirm a fix takes effect.** An override that loses to a more specific rule, or a setting another step resets, looks done and isn't. Check the outcome, not the diff.
- **Skills are drafts; amend them in use.** When a loaded skill proves wrong, stale or missing a step, fix the skill in the same session and say so in one line. Any model may add or correct a line, but a T3 model does it on a branch for T2 or stronger review (`model-tiers.md`); restructuring, retriggering or deleting is for the strongest model or the user (the `skill-forge` skill has the split). A lesson kept only in the session that learned it is lost.
- **Work deferred to someone else is written where they will read it, in the same step that defers it.** That place is a log row, a TODO, a PR description or a `## Pending` line, never only the chat. A chat reply is not durable, and writing "left for the reviewer" does not hand anything over. On 2026-11-11 a contradicting rule was noted as "left for the T1 proofread" in a reply only. It survived because the user asked, and most users of these frameworks would not.
- **Keep the Claude setup current with Claude Code.** Claude Code ships new hook events, settings and tools often, and ConfigMe only gains from them if someone notices: `settings.json` went untracked for weeks, and hooks went unused until the user stumbled on them. When a session starts with a "Claude Code updated" note (the `claude-version-watch` hook), check the changelog and suggest what ConfigMe should adopt or stop doing by hand. Any new Claude config goes into ConfigMe in the same change, never only into `~/.claude/`.
- **The desktop app's own tools are heavy and some are flawed; look for the leaner route first.** For an agent test or a measurement, a headless terminal run (`claude -p ... --output-format json`, with `--disallowedTools` and `--strict-mcp-config` to control what loads) beats the built-in sub-agent: it gives exact token counts, a chosen model and effort, and a clean context. From inside a desktop-app session run it through `claude-probe` or `claude-lean`: a plain `claude -p` there can report an expired login that is not one (`bin/claude-probe` says why). Check it works before planning a test, and tell the user at once if it does not. On 2026-11-10 a session ran sub-agent tests all day, met the login error only when a measurement failed, and reported the CLI as logged out without having read `bin/`; the user said it should have come up earlier. Measured the same day: one page-publishing tool is 12k of a 44k terminal start, and a deny rule removes it.
